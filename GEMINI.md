# DDLC Agent Studio — AI Context & Architectural Guide

## 1. What This Project Is

**DDLC Agent Studio** is an engineering platform centered around a **Meta-Agent** (an agent factory) that designs, builds, validates, and maintains specialized Data Development Lifecycle (DDLC) agents from declarative YAML specifications and data contracts.

Generated DDLC agents handle data engineering workflows (ingestion, validation, PII governance, transformation, publishing) across varying runtimes (stateful graphs, batch pipelines, or event streams).

## 2. Core Architectural Principles (Evergreen)

1. **The Graph Orchestrates, the LLM Reasons**

   * Workflow control is 100% deterministic (managed by a Coordinator state machine with explicit edges, retry bounds, and human gates).

   * LLMs never decide workflow routing or skip steps; they operate strictly inside scoped domain Specialists.

2. **Deterministic Compilation Over Probabilistic Generation ("Skeleton vs. Muscle")**

   * **The Skeleton (Deterministic)**: Orchestration wiring, data models, quality suites, telemetry hooks, and database migrations are compiled deterministically from YAML contracts (via templates, AST validation, SQLGlot, and Alembic). Never use LLMs to generate boilerplate scaffolding or execute raw DDL.

   * **The Muscle (Isolated Leaf Logic)**: LLMs (and human developers) write only isolated, unit-tested business logic handlers that plug into the read-only skeleton.

3. **Single Source of Truth (`impl_docs/`)**

   * Day-0 intake uses a high-level user specification to capture intent, resolve ambiguities, and design architecture.

   * Post-build, structured YAML implementation documents (`impl_docs/` covering agent manifest, stages, contracts, governance, config, and tests) become the permanent single source of truth for Day-2 maintenance.

4. **The Context Funnel & State Projection**

   * A central **Blackboard** accumulates workflow state for resumability and traceability.

   * Each Specialist receives only a narrow **State Projection** (the exact slice of context needed for its task) to minimize token usage and prevent context drift.

5. **Unified Storage & Three-Tier Metadata**

   * PostgreSQL + `pgvector` serves as the unified persistence engine for state checkpoints, domain-tagged RAG knowledge, and the **Metadata Framework**:

     * **Tier 1**: Generic agent operational telemetry and immutable audit logs.

     * **Tier 2**: Shared DDLC catalog (agents, reusable components, contracts) and cross-agent lineage.

     * **Tier 3**: Agent-specific operational schemas.

## 3. System Mental Model

* **Coordinator**: Deterministic state machine enforcing phase progression, loop safety valves, and human approval gates.

* **Specialists**:

  * *Spec Analyst*: Validates intake specs and surfaces gaps/questions.

  * *Researcher*: Evaluates tool feasibility and standards via RAG.

  * *Architect*: Selects architecture patterns, runtimes, and shared components.

  * *Documentarian*: Translates approved designs into runtime-agnostic YAML `impl_docs/`.

  * *Builder*: Compiles the deterministic orchestration skeleton and synthesizes custom leaf handlers.

  * *Validator*: Verifies contract compliance, governance hooks, and automated tests.

* **DCM Schema Engine**: Declarative database lifecycle tool that compiles YAML data contracts into dialect-safe DDL and versioned migrations.

## 4. Working Guidelines for AI Assistants

When writing code, reviewing designs, or proposing changes in this repository:

* **Preserve the Determinism Boundary**: Do not introduce LLM calls where deterministic parsing, AST compilation, or rule-based validation can do the job.

* **Respect the Skeleton/Muscle Split**: Never manually edit files marked as deterministically autogenerated; make structural changes in the YAML contracts/templates, and keep imperative business logic inside isolated handler modules.

* **Zero Hardcoding**: All URIs, thresholds, model assignments, and credentials must be externalized into configuration and secrets references.

* **Reuse Before Creating**: Check shared component catalogs and common utilities before generating duplicate functionality.

* **Consult Design Docs for Details**: Refer to the `design-docs/` directory for current schemas, data dictionaries, and component specifications before making structural changes.
