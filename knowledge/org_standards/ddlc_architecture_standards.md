# DDLC Agent Studio — Architecture Standards

Evergreen engineering standards governing both the **Layer 1 Meta-Agent Factory** and all generated **Layer 2 DDLC AI Agents**.

---

## 1. The Graph Orchestrates, the LLM Reasons

Workflow control is **100% deterministic** and lives inside a Coordinator state machine (`langgraph` `StateGraph` edges or linear `python_litellm` runner steps) with explicit retry bounds, safety valves, and human approval gates.

- **Coordinator**: Reads discrete state flags (`review_decision`, `reflection_count`, `diagnostics`) via pure Python routing functions (`route_dry_run`, `route_review`). It holds no prompt, makes no LLM calls, and never interprets free-text content.
- **Specialists**: LLM reasoning is strictly confined to scoped domain Specialists (`Spec Analyst`, `Researcher`, `Architect`, `Documentarian`, `Builder` Leaf Coder, `Validator`) and `llm_reasoning` stage nodes using LiteLLM + Instructor.
- **No Agentic Control Drift**: Never delegate phase transitions, loop termination, or schema DDL execution to autonomous inner LLM loops.

---

## 2. Deterministic Compilation Over Probabilistic Generation ("Skeleton vs. Muscle")

Generated DDLC agents strictly isolate immutable structural wiring from editable domain logic (Decisions 21 and 26):

### The Skeleton (Read-Only, Zero-LLM)
Compiled deterministically by the Scaffold Compiler (Jinja2 + `ast.parse`) and DCM Schema Engine (YAML + SQLGlot + Alembic):
- `src/models/contracts_pydantic.py` (Pydantic v2 / Instructor contracts)
- `src/core/config.py` (`AgentSettings` + `FrameworkRuntimeSettings`)
- `src/core/telemetry.py` (`MetadataCallbackHandler` integration)
- `src/graph.py` (`StateGraph`, conditional edges, `interrupt()` gates, Claim Check staging)
- `tests/contracts/test_contracts.py`

All Skeleton files carry the header `# DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs.` and must never be hand-edited. Structural changes happen in `impl_docs/` and trigger deterministic recompilation.

### The Muscle (Editable, Leaf-Scoped)
Synthesized on demand by the LLM Leaf Coder (or maintained by engineers) only where bespoke imperative logic or prompts exist:
- `src/tools/*.py` (custom tools declared with `type: custom_code` and `handler: "tools/<mod>.py::<func>"`)
- `src/prompts/stage_<id>.jinja2` (Universal Prompt Contract templates)
- `tests/unit/test_*.py`

During Day-2 change requests, the Leaf Coder runs in `patch` mode (injecting existing code and tests) rather than `create` mode so emergency 2 AM production hotfixes are never overwritten. Advisory CI checks (`ddlc check-drift`) and `ddlc sync-docs` keep `src/tools/` and `impl_docs/stages/` aligned (Decision 25).

## 3. Single Source of Truth (`impl_docs/` and `contracts/`)

- **Day-0 Intake Retirement**: `spec.yaml` is strictly a Day-0 bootstrapping intake form. Once Gate 3 (`impl_docs` review) is approved and Phase 8 Delivery completes, `spec.yaml` is archived in Tier 1 `artifact_registry` and retired from active use (Decision 20).
- **Permanent Agent Source of Truth**: The 5-document `impl_docs/` suite (`agent.yaml`, `stages/stage_<id>.yaml`, `contracts/<name>.yaml`, `config.yaml`, `tests.yaml`) committed inside the agent's Git repository is the sole authoritative source for all Day-2 maintenance (via Git PRs or Chainlit change flows).
- **Database Schema Source of Truth**: Relational metadata schemas across Tiers 1–3 are declared in `contracts/*.yaml` and provisioned deterministically via the DCM Schema Engine (`dcm validate`, `dcm plan`, `dcm revision`, `dcm apply`), never via raw manual DDL or LLM SQL execution.

---

## 4. Context Funnel, State Projection & Claim Check

Each workflow phase acts as a narrowing funnel (`Spec` -> `Parsed Spec` -> `Architecture` -> `Impl Docs` -> `Code`), preventing context bloat and drift:

- **Append-Only Blackboard**: LangGraph state preserves clarification rounds, revisions, and diagnostics across `PostgresSaver` checkpoints for full resumability and auditability.
- **State Projection**: Specialists receive only the minimal context slice required for their responsibility (e.g., `Builder` sees only `impl_docs/` and shared components, never Q&A transcripts or rejected architectures).
- **Isolated RAG Budgets**: Specialists query only authorized `rag_knowledge` domains with hard token ceilings (`Researcher`: 1,000 tokens / `top_k=3`; `Architect`: 1,400 tokens / `top_k=4`; `Builder`: 1,000 tokens / `top_k=3`), rendered as escaped `<rag_context>` XML slices.
- **Claim Check State Pointers**: Multi-file generated bundles (`dbt_artifact_bundle`) are staged externally to disk/storage rather than stored inline in `AgentState`. State carries lightweight SHA-256 pointers (`bundle_id`, `storage_uri`, `file_manifest`, `artifact_sha256`), keeping checkpoints sub-millisecond (Decision 22).

---

## 5. Unified PostgreSQL + pgvector & Decoupled Metadata

A single PostgreSQL 17 + `pgvector` instance serves all persistence needs — LangGraph checkpoints, RAG hybrid search (`rag_knowledge`), and the **Three-Tier Metadata Framework**:
- **Tier 1 (`agent_metadata`)**: Generic operational telemetry, artifact registry/manifest, decision log, and immutable audit log.
- **Tier 2 (`ddlc_shared_metadata`)**: DDLC catalog (`agent_registry`, `component_registry` with `vector(1536)`, `contract_registry`), lineage (`contract_lineage`, `agent_dependency`, `component_usage`), build/stage metrics, and gate/governance audits.
- **Tier 3 (`ddlc_<agent_name>_metadata`)**: Isolated agent-specific tables compiled by DCM.

Per **Decision 30**, passive observability (`MetadataCallbackHandler`) is strictly decoupled from transactional business writes (`node_delivery` / `node_deliver_stage`). Callback telemetry failures log warnings and never abort execution; Git PRs, Tier 2 catalog/lineage commits, and RAG Two-Phase Commit ingestion fail fast with explicit errors.

---

## 6. Zero Hardcoding & Reuse-First Standards

- **Zero Hardcoding**: All URIs, dialects, model tiers, retry thresholds, and credentials must be externalized into `config/*.yaml`, `config.yaml` (`${config.*}`), and `${secrets.*}` environment references.
- **Reuse Before Creating**: Before generating custom tools, the Researcher and Architect must search Tier 2 `component_registry` (via semantic similarity and SQL) and bind existing shared components (`usage_type: import | extend | wrap`) declared centrally in `agent.yaml`.
