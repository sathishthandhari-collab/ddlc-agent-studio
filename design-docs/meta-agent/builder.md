## 1. Document Purpose & Architectural Pivot

The Meta-Agent's Documentarian outputs structured YAML implementation documents (`impl_docs/`): `agent.yaml`, `stages/*.yaml`, `contracts/*.yaml`, `governance.yaml`, `config.yaml`, and `tests.yaml`. 

This document defines how the **Builder Specialist** (Phase 6 of the Meta-Agent workflow) transforms those implementation documents into a deployable, production-ready Python codebase.

### 1.1 The Architectural Pivot: Split Compiler + Leaf Coder

Earlier conceptual drafts envisioned the Builder as a single, large-language-model-driven code generator that ingested all implementation documents and outputted Python files via iterative LLM prompts. 

Just as the **DCM Schema Engine** ([`dcm_agent.md`](file:///s:/DATA/agents/ddlc-agent-studio/design-docs/dcm-agent/dcm_agent.md)) rejected LLM-based SQL generation in favor of a 100% deterministic **SQLGlot + Alembic** compiler, **we explicitly split the Builder Specialist into two distinct architectural tiers**:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                BUILDER SPECIALIST (PHASE 6)                            │
│                                                                                        │
│   ┌────────────────────────────────────────────────────────────────────────────────┐   │
│   │                 TIER 1: DETERMINISTIC SCAFFOLD COMPILER                        │   │
│   │                          (Jinja2 + Python AST)                                 │   │
│   │                                                                                │   │
│   │  • Zero LLM calls. Pure, instantaneous Python compilation.                     │   │
│   │  • Emits the complete read-only orchestration skeleton.                        │   │
│   │  • Compiles Pydantic contracts, Great Expectations suites, StateGraph DAG,     │   │
│   │    governance decorators, telemetry hooks, and config loaders.                 │   │
│   │  • Header: # DO NOT EDIT. Autogenerated deterministically by DDLC Compiler.    │   │
│   └───────────────────────────────────────┬────────────────────────────────────────┘   │
│                                           │ identifies bespoke stages                  │
│                                           │ (transform_handler hooks)                  │
│                                           ▼                                            │
│   ┌────────────────────────────────────────────────────────────────────────────────┐   │
│   │                    TIER 2: LLM LEAF CODER & TEST SYNTHESIZER                   │   │
│   │                     (Instructor + Structured Output Prompts)                   │   │
│   │                                                                                │   │
│   │  • Invoked ONLY for stages requiring custom imperative logic.                  │   │
│   │  • Scoped strictly to leaf functions (e.g. compute_tiers, custom pagination). │   │
│   │  • Synthesizes editable handlers (handlers/*.py) and unit tests.               │   │
│   │  • Regular, version-controlled Python code: editable by Meta-Agent or humans.  │   │
│   └────────────────────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 Rationale: Why Split the Builder?

| Engineering Concern | All-LLM Code Generation (Rejected) | Deterministic Compiler + LLM Leaf Coder (Selected) |
|---|---|---|
| **Determinism & Syntax Reliability** | LLMs occasionally hallucinate import paths, invert conditional branching, misplace retry arguments, or introduce subtle indentation syntax errors in complex LangGraph state machines. | **Mathematical Determinism**: The orchestration skeleton is compiled via Jinja2 templates verified by Python `ast.parse`. Syntax is 100% guaranteed. |
| **Contract Fidelity** | LLMs may drop optional attributes, alter field types (`datetime` vs `str`), or hallucinate validation decorators when translating YAML schemas to Pydantic. | **Direct AST Compilation**: Pydantic models and Great Expectations suites are compiled field-for-field directly from `contracts/*.yaml`. Zero drift. |
| **Token Cost & Latency** | Generating thousands of lines of boilerplate scaffolding (graphs, contracts, config, logging) consumes ~25,000–50,000 output tokens and takes 60–90 seconds per run. | **Sub-Second Scaffold Emission**: The scaffold compiler runs locally in <250ms with zero API token consumption. LLM tokens are spent solely on bespoke business logic (~500 tokens). |
| **Maintainability (The "2 AM Bug" Rule)** | When an agent fails in production at 2 AM, on-call engineers cannot easily debug a monolithic 1,200-line generated agent script where state wiring, logging, and logic are intertwined. | **The Skeleton vs. The Muscle**: The orchestration skeleton is immutable and verified. On-call engineers can inspect and hotfix `handlers/enrich_customer.py` directly without fear of breaking state transitions. |
| **Day-2 Change Requests** | Changing a single column or retry threshold in an all-LLM system requires regenerating the entire agent codebase, risking regression across unrelated stages. | **Surgical Recompilation**: Schema or retry changes re-run only the deterministic compiler. Leaf handlers remain untouched. |

## 2. Core Paradigm: "The Skeleton" vs. "The Muscle"

The generated codebase enforces a strict separation of concerns between **structural orchestration** and **imperative execution**.

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              GENERATED AGENT CODEBASE                                  │
│                                                                                        │
│  ┌──────────────────────────────────────────────────────────────────────────────────┐  │
│  │                    THE SKELETON (100% Read-Only, Deterministic)                  │  │
│  │                                                                                  │  │
│  │  # DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs. │  │
│  │                                                                                  │  │
│  │  • src/models/contracts.py      (Pydantic v2 data models)                        │  │
│  │  • src/core/config.py           (Pydantic BaseSettings & secrets resolution)     │  │
│  │  • src/core/governance.py       (Tier 1/2 telemetry hooks & PII scan wrappers)  │  │
│  │  • src/graph.py / pipeline.py   (StateGraph wiring, routing edges, retries)      │  │
│  │  • tests/contracts/test_*.py    (Great Expectations contract validation suites)  │  │
│  └──────────────────────────────────────────┬───────────────────────────────────────┘  │
│                                             │ invokes via dynamic dispatch             │
│                                             ▼                                          │
│  ┌──────────────────────────────────────────────────────────────────────────────────┐  │
│  │                    THE MUSCLE (Editable, LLM or Human Authored)                  │  │
│  │                                                                                  │  │
│  │  # Editable business logic — hotfixable by engineers or Meta-Agent               │  │
│  │                                                                                  │  │
│  │  • src/handlers/enrich_customer.py  (Bespoke transformation function)            │  │
│  │  • src/handlers/parse_custom_api.py (Bespoke pagination/parsing logic)           │  │
│  │  • tests/unit/test_enrich_customer.py (Targeted unit tests & edge case mocks)   │  │
│  └──────────────────────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 The Skeleton (Read-Only)
- **Source**: Compiled directly from `agent.yaml`, `stages/*.yaml`, `contracts/*.yaml`, `governance.yaml`, and `config.yaml`.
- **Role**: Defines the pipeline state machine, data transfer objects, quality verification suites, configuration bindings, and telemetry interception.
- **Mutability**: **Immutable**. Sealed with an autogenerated header. CI blocks pull requests that modify skeleton files without corresponding `impl_docs/` changes.
- **Standard Connectors**: Standard I/O (S3, Kafka, Postgres, Snowflake) and Tier 2 shared components (e.g., `shared:pii_masker_v2`) are emitted directly into the skeleton using hardened SDK boilerplate.

### 2.2 The Muscle (Editable Handlers)
- **Source**: Synthesized by the LLM Leaf Coder during Phase 6, or authored directly by engineers.
- **Role**: Houses domain-specific imperative business logic (e.g., customer tier calculation, proprietary risk scoring, legacy API pagination).
- **Interface**: Plugged into the skeleton via standardized, typed hook signatures (`transform_handler`).
- **Mutability**: **Fully Editable**. Version-controlled Python code. Human developers or the Meta-Agent can refactor, optimize, or hotfix these functions without altering the state graph.

## 3. The Deterministic Scaffold Compiler

The Deterministic Scaffold Compiler is a pure Python engine located in `src/specialists/builder/compiler/`. It parses YAML implementation documents and renders pre-tested Jinja2 templates into Python ASTs, validating syntax before writing files to disk.

```
┌─────────────────────────────────┐
│           impl_docs/            │
│                                 │
│  • agent.yaml                   │
│  • stages/*.yaml                │
│  • contracts/*.yaml             │
│  • governance.yaml              │
│  • config.yaml                  │
│  • tests.yaml                   │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│  Scaffold Compiler (Jinja2)     │
│                                 │
│  1. Ingests & validates YAML    │
│  2. Selects runtime template    │
│  3. Compiles Pydantic models    │
│  4. Compiles GE test suites     │
│  5. Wires state machine DAG     │
│  6. Generates telemetry hooks   │
│  7. Formats & validates AST     │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│     The Orchestration Skeleton  │
│      (# DO NOT EDIT files)      │
└─────────────────────────────────┘
```

### 3.1 Contract Compilation (`contracts/*.yaml` → Pydantic + Great Expectations)

For every contract file in `contracts/contract_<name>.yaml`, the compiler deterministically emits:
1. **Pydantic v2 Models** in `src/models/contracts.py`:
   - Exact type mapping:
     - `string` → `str`
     - `integer` → `int`
     - `float` → `float`
     - `boolean` → `bool`
     - `timestamp` → `datetime.datetime`
     - `date` → `datetime.date`
     - `json` → `Dict[str, Any]`
   - Nullability constraints: Optional fields wrap in `Optional[...] = None`.
   - Quality rules to Pydantic Field constraints (`ge`, `le`, `min_length`, `max_length`, `pattern`).
   - Custom field validators for enum/allowed values (`check: field IN ('A', 'B')`).

2. **Great Expectations Test Suite** in `tests/contracts/test_contracts.py`:
   - Emits programmatic expectation checkpoints:
     - `expect_column_values_to_not_be_null`
     - `expect_column_values_to_match_regex`
     - `expect_column_values_to_be_in_set`
     - `expect_table_row_count_to_be_between`
   - Configured to run against batch payloads or in-memory pandas/polars DataFrames prior to stage execution.

#### Deterministic Contract Generation Example

Given `contracts/customer_validated.yaml`:
```yaml
contract:
  id: customer_validated
  version: "1.0.0"

schema:
  fields:
    - name: customer_id
      type: string
      nullable: false
      rules:
        - name: format_check
          rule: "regex:^CUST-[0-9]{8}$"
    - name: email
      type: string
      nullable: false
    - name: credit_score
      type: integer
      nullable: true
      rules:
        - name: range_check
          rule: "between:300,850"
```

The Compiler deterministically outputs `src/models/contracts.py`:

```python
from datetime import date, datetime
from typing import Any, Dict, Optional
from pydantic import BaseModel, Field, field_validator
import re

class CustomerValidated(BaseModel):
    """Autogenerated Pydantic model for contract: customer_validated v1.0.0"""
    customer_id: str = Field(..., description="Customer unique ID")
    email: str = Field(..., description="Customer email address")
    credit_score: Optional[int] = Field(None, ge=300, le=850, description="Credit rating")

    @field_validator("customer_id")
    @classmethod
    def validate_customer_id(cls, v: str) -> str:
        pattern = r"^CUST-[0-9]{8}$"
        if not re.match(pattern, v):
            raise ValueError(f"Field 'customer_id' violates regex pattern {pattern}")
        return v
```

### 3.2 Configuration Compilation (`config.yaml` → Pydantic `BaseSettings`)

The compiler reads `config.yaml` and produces `src/core/config.py`:
- Emits a Pydantic `BaseSettings` class reading runtime parameters from environment variables with defaults.
- Generates structured configuration classes for external endpoints (`sources`, `destinations`).
- Emits secret resolvers that pull from environment variables or AWS Secrets Manager / HashiCorp Vault.
- Guarantees **Zero Hardcoded Secrets or URIs**.

### 3.3 Governance & Metadata Compilation (`governance.yaml` → Telemetry Decorators)

The compiler reads `governance.yaml` and produces `src/core/governance.py`:
- **Tier 1 Callbacks**: Automatically injects start and end telemetry hooks for every stage into PostgreSQL tables `agent_metadata.agent_run_header` and `agent_metadata.execution_log`.
- **Tier 2 Audit Logger**: Emits audit emission helpers pointing to `ddlc_shared_metadata.governance_audit`.
- **PII Guardrails**: If `pii_handling.enabled: true`, the compiler emits verification wrappers that scan stage outputs using regex heuristics (email, SSN, credit cards) to ensure unmasked data is never emitted to downstream destinations.

```python
# ==============================================================================
# DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs.
# File: src/core/governance.py
# ==============================================================================
import functools
import time
import logging
from typing import Any, Callable, Dict
from src.core.telemetry_client import Tier1MetadataClient, Tier2AuditClient

logger = logging.getLogger("governance")
tier1 = Tier1MetadataClient()
tier2 = Tier2AuditClient()

def stage_governance_guard(stage_id: str, log_inputs: bool = True, log_outputs: bool = True):
    """Wraps stage execution with Tier 1 telemetry and Tier 2 audit logging."""
    def decorator(func: Callable):
        @functools.wraps(func)
        def wrapper(state: Dict[str, Any], *args, **kwargs):
            run_id = state.get("run_id")
            tier1.log_stage_start(run_id=run_id, stage_id=stage_id)
            start_time = time.time()
            try:
                result = func(state, *args, **kwargs)
                duration_ms = int((time.time() - start_time) * 1000)
                tier1.log_stage_complete(run_id=run_id, stage_id=stage_id, duration_ms=duration_ms)
                return result
            except Exception as exc:
                duration_ms = int((time.time() - start_time) * 1000)
                tier1.log_stage_failure(run_id=run_id, stage_id=stage_id, error=str(exc), duration_ms=duration_ms)
                tier2.log_audit_event(run_id=run_id, event="stage_failure", details={"stage_id": stage_id, "error": str(exc)})
                raise
        return wrapper
    return decorator
```

## 4. The Three Runtime Generation Strategies

The compiler supports three distinct runtime strategies configured in `agent.yaml` (`architecture.runtime`):

```yaml
architecture:
  runtime: "langgraph" # Options: langgraph | python_pipeline | streaming
```

### 4.1 Strategy 1: LangGraph (`langgraph`)

Designed for stateful agent workflows requiring branching, looping, human approval gates, checkpointer recovery, or tool orchestration.

#### StateGraph Skeleton Wiring
- **State Definition**: Emits a `TypedDict` or Pydantic `AgentState` containing the accumulating payload, metadata, run identifiers, and error containers.
- **Node Emission**: Wraps each stage in a node function decorated with `@stage_governance_guard`.
- **Edge Routing**: Emits deterministic conditional edges (e.g., checking `quality_score >= 0.95` or evaluating routing rules).
- **Human Approval Gates**: For stages with `autonomy: human_required` or stages declared in `governance.yaml` (`approval_gates`), the compiler inserts LangGraph `interrupt()` calls and checkpointer pause hooks.
- **Retry Wrappers**: Applies exponential backoff retry policies based on `stage.error_strategy`.

```python
# ==============================================================================
# DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs.
# File: src/graph.py
# ==============================================================================
from typing import TypedDict, Optional, List, Dict, Any
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver
from src.core.governance import stage_governance_guard
from src.core.config import settings
from src.handlers.enrich_customer import compute_tiers  # Leaf hook import

class AgentState(TypedDict):
    run_id: str
    raw_records: List[Dict[str, Any]]
    validated_records: List[Dict[str, Any]]
    enriched_records: List[Dict[str, Any]]
    quality_score: float
    error_log: List[Dict[str, Any]]

@stage_governance_guard("enrich_stage")
def node_enrich_stage(state: AgentState) -> Dict[str, Any]:
    """Orchestration node delegating to editable muscle handler."""
    records = state["validated_records"]
    enriched = [compute_tiers(r) for r in records]
    return {"enriched_records": enriched}

def route_quality_gate(state: AgentState) -> str:
    """Deterministic routing edge compiled from stages/stage_validate.yaml."""
    if state["quality_score"] < 0.95:
        return "quarantine_node"
    return "enrich_stage"

def build_graph() -> StateGraph:
    workflow = StateGraph(AgentState)
    workflow.add_node("validate_stage", node_validate_stage)
    workflow.add_node("enrich_stage", node_enrich_stage)
    workflow.add_node("quarantine_node", node_quarantine)
    
    workflow.set_entry_point("validate_stage")
    workflow.add_conditional_edges("validate_stage", route_quality_gate)
    workflow.add_edge("enrich_stage", END)
    workflow.add_edge("quarantine_node", END)
    
    return workflow.compile(checkpointer=PostgresSaver.from_conn_string(settings.DATABASE_URI))
```

### 4.2 Strategy 2: Python Pipeline (`python_pipeline`)

Designed for linear, high-throughput batch ETL/ELT pipelines that do not require stateful agent graph machinery.

#### Characteristics
- Emits a clean, sequential pipeline class `src/pipeline.py`.
- Stages execute in topological sequence.
- Wrapped in `@tenacity.retry` decorators based on `stage.error_strategy`.
- Supports in-memory streaming batches via Polars or Pandas.
- Emits a CLI runner (`src/main.py`) powered by Typer or Click.

```python
# ==============================================================================
# DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs.
# File: src/pipeline.py
# ==============================================================================
import logging
from typing import Dict, Any
from src.core.governance import stage_governance_guard
from src.handlers.enrich_customer import compute_tiers

logger = logging.getLogger("pipeline")

class PipelineRunner:
    """Linear batch execution pipeline compiled from agent.yaml."""

    def __init__(self, run_id: str):
        self.run_id = run_id
        self.context: Dict[str, Any] = {"run_id": run_id}

    @stage_governance_guard("enrich_stage")
    def run_enrich_stage(self):
        records = self.context["validated_records"]
        self.context["enriched_records"] = [compute_tiers(r) for r in records]

    def execute(self):
        logger.info(f"Starting pipeline execution run_id={self.run_id}")
        self.run_ingest_stage()
        self.run_validate_stage()
        self.run_enrich_stage()
        self.run_publish_stage()
        logger.info("Pipeline completed successfully")
```

### 4.3 Strategy 3: Streaming (`streaming`)

Designed for continuous event processing via Kafka, AWS Kinesis, or Pub/Sub.

#### Characteristics
- Emits asynchronous message consumption loop (`src/streaming_worker.py`).
- Automatic JSON/Avro deserialization into Pydantic contract models.
- Emits Dead-Letter Queue (DLQ) publisher for records failing contract validation.
- Dispatches valid records to custom transformation leaf handlers.
- Emits windowing and graceful shutdown handlers.

```python
# ==============================================================================
# DO NOT EDIT. Autogenerated deterministically by DDLC Compiler from impl_docs.
# File: src/streaming_worker.py
# ==============================================================================
import asyncio
import json
from aiokafka import AIOKafkaConsumer, AIOKafkaProducer
from pydantic import ValidationError
from src.models.contracts import CustomerValidated, CustomerEnriched
from src.handlers.enrich_customer import compute_tiers
from src.core.config import settings

async def start_streaming():
    consumer = AIOKafkaConsumer(
        "customer.validated",
        bootstrap_servers=settings.KAFKA_BOOTSTRAP_SERVERS,
        group_id="ddlc_enricher_group"
    )
    producer = AIOKafkaProducer(bootstrap_servers=settings.KAFKA_BOOTSTRAP_SERVERS)
    await consumer.start()
    await producer.start()
    
    try:
        async for msg in consumer:
            try:
                payload = json.loads(msg.value.decode("utf-8"))
                validated_record = CustomerValidated(**payload)
                enriched_record: CustomerEnriched = compute_tiers(validated_record)
                await producer.send_and_wait("customer.enriched", enriched_record.model_dump_json().encode("utf-8"))
            except ValidationError as ve:
                # Automatic DLQ routing for contract violations
                await producer.send_and_wait("customer.dlq", msg.value)
    finally:
        await consumer.stop()
        await producer.stop()
```

## 5. The Muscle: LLM Leaf Coder & Custom Handler Synthesis

The LLM Leaf Coder (`src/specialists/builder/leaf_coder/`) is an intelligent specialist worker invoked **strictly on demand**.

### 5.1 Invocation Boundary

The Scaffold Compiler scans `stages/*.yaml`. It invokes the LLM Leaf Coder if and only if a stage requires bespoke imperative logic:

```
                          ┌──────────────────────────┐
                          │   Stage Specification    │
                          │   (stages/stage_*.yaml)  │
                          └─────────────┬────────────┘
                                        │
                         Does it have a custom hook?
                      (transform_handler: "...") OR
             (type: transformation/custom without shared tool)
                                        │
                       ┌────────────────┴────────────────┐
                      YES                               NO
                       │                                 │
                       ▼                                 ▼
         ┌───────────────────────────┐     ┌───────────────────────────┐
         │   INVOKE LLM LEAF CODER   │     │  USE STANDARD SDK / CONNECTOR │
         │                           │     │                           │
         │ • Scoped state projection │     │ • Emit standard S3/SQL/   │
         │ • Generates handlers/*.py │     │   Kafka read/write block  │
         │ • Generates unit tests    │     │ • Import Tier 2 component │
         └───────────────────────────┘     │ • Zero LLM calls needed   │
                                           └───────────────────────────┘
```

### 5.2 The Hook Protocol

To wire the Skeleton to the Muscle, the Documentarian writes an explicit hook in the stage YAML:

```yaml
# In stages/stage_enrich.yaml
stage:
  id: enrich
  name: "Enrich Customer Tier"
  type: transformation
  transform_handler: "handlers/enrich_customer.py::compute_tiers"
  
input:
  contract: customer_validated
output:
  contract: customer_enriched

processing:
  logic_description: >
    Calculate loyalty tier based on credit_score and historical purchases:
    - Tier Platinum: credit_score >= 750 AND lifetime_spend > 10000
    - Tier Gold: credit_score >= 700 OR lifetime_spend > 5000
    - Tier Silver: All other active customers
    Add calculate_date timestamp as current UTC time.
```

### 5.3 State Projection for the Leaf Coder

Following the **Context Funnel Principle** ([`architecture.md` Section 5.1](file:///s:/DATA/agents/ddlc-agent-studio/design-docs/meta-agent/architecture.md)), the LLM Leaf Coder receives a narrow, laser-focused state projection containing **only**:
1. The **Input Pydantic Contract** code (`CustomerValidated`).
2. The **Output Pydantic Contract** code (`CustomerEnriched`).
3. The **Stage Logic Description** (`processing.logic_description`).
4. Any declared helper tools or math libraries.

It does **NOT** see the blackboard, other stages, graph orchestration, or conversation history. The prompt is under 1,500 tokens.

### 5.4 Leaf Coder Output: Handler Code + Unit Test

The Leaf Coder generates two version-controlled Python files:

#### 1. The Handler (`src/handlers/enrich_customer.py`)
```python
"""
DDLC Custom Handler: compute_tiers
Generated by DDLC Leaf Coder. Editable by engineering team.
Stage: enrich
"""
from datetime import datetime, timezone
from src.models.contracts import CustomerValidated, CustomerEnriched

def compute_tiers(record: CustomerValidated) -> CustomerEnriched:
    """Calculates customer loyalty tier based on credit score and spend metrics."""
    credit = record.credit_score or 0
    spend = getattr(record, "lifetime_spend", 0.0)

    if credit >= 750 and spend > 10000.0:
        tier = "Platinum"
    elif credit >= 700 or spend > 5000.0:
        tier = "Gold"
    else:
        tier = "Silver"

    return CustomerEnriched(
        customer_id=record.customer_id,
        email=record.email,
        credit_score=record.credit_score,
        loyalty_tier=tier,
        calculation_timestamp=datetime.now(timezone.utc)
    )
```

### 5.5 The "2 AM On-Call Rule"

Because `handlers/enrich_customer.py` is standard, isolated Python code:
1. **Zero Orchestration Risk**: A developer fixing a boundary condition at 2 AM does not touch LangGraph edges, checkpointer settings, or metadata emission.
2. **Instant Test Verification**: Running `$ pytest tests/unit/test_enrich_customer.py` takes 50 milliseconds without requiring Docker, databases, or cloud credentials.
3. **GitOps Friendly**: Changes appear in code reviews as clean, readable 5-line diffs in `handlers/`.

### 8.1 Surgical Fix Loop

If a unit test in `tests/unit/test_enrich_customer.py` fails:
- The Validator produces specific error diagnostics (e.g., `AssertionError: loyalty_tier 'Silver' != 'Gold' on boundary credit_score=700`).
- The Coordinator routes **strictly to the LLM Leaf Coder** with the failure log.
- **The Scaffold Compiler is NOT re-run**. The Skeleton remains intact.
- The Leaf Coder patches `handlers/enrich_customer.py` and returns it to the Validator.
- Maximum fix attempts (default: 3) are enforced by the coordinator safety valve.

## 9. Day-2 Lifecycle & Maintenance (Change Requests & Hotfixes)

In production, agents evolve. The separation between Skeleton and Muscle enables clean, risk-free Day-2 maintenance.

### 9.1 Scenario A: Schema Evolution or Graph Re-wiring
- **Trigger**: A developer adds a new column to `contracts/customer_validated.yaml` or updates a retry threshold in `stages/stage_validate.yaml` via Pull Request.
- **Action**: CI runs the **Deterministic Scaffold Compiler**:
  - `src/models/contracts.py` and `src/graph.py` are deterministically re-emitted in 100ms.
  - The DCM Schema Engine compiles database migrations if persistent tables changed.
  - Existing custom handlers in `src/handlers/` are **untouched**.
  - Zero LLM tokens spent.

### 9.2 Scenario B: Imperative Logic Hotfix (The 2 AM Patch)
- **Trigger**: A business analyst discovers that customers with exactly 5,000 spend should be Gold tier, not Silver.
- **Action**: An on-call engineer opens `src/handlers/enrich_customer.py`:
  - Changes `spend > 5000.0` to `spend >= 5000.0`.
  - Updates the corresponding test assertion in `tests/unit/test_enrich_customer.py`.
  - Runs `$ pytest tests/unit/` locally. Tests pass.
  - Commits directly to Git.
  - **The orchestration skeleton, graph, and contracts are completely unaffected.**

### 9.3 Scenario C: Conversational Feature Addition via Meta-Agent
- **Trigger**: User prompts Meta-Agent: *"Add a VIP flag to customers with over \$50k spend"*.
- **Action**:
  - Spec Analyst and Documentarian update `contracts/customer_enriched.yaml` and `stages/stage_enrich.yaml`.
  - Deterministic Compiler updates `src/models/contracts.py`.
  - LLM Leaf Coder updates `src/handlers/enrich_customer.py` and synthesizes new unit tests.
  - Validator checks the entire agent. Done.

## 10. Design Decisions Log (Builder Scope)

All architectural decisions governing the Builder Specialist are recorded below:

| # | Architectural Decision | Selected Approach | Alternative Rejected | Rationale |
|---|---|---|---|---|
| **B-1** | **Scaffold Generation Engine** | Deterministic Jinja2 + Python AST Compiler | All-LLM code generation from prompts | Guarantees 100% syntax determinism, zero hallucinations on graph wiring or data contracts, and sub-second execution with zero token cost. |
| **B-2** | **Imperative Logic Generation** | Isolated LLM Leaf Coder with narrow State Projection | Hardcoded rule templates or monolithic generation | Complex transformations (tiering, math, custom parsing) cannot be expressed cleanly in YAML; LLM excels at writing isolated leaf functions when constrained by contracts. |
| **B-3** | **Read-Only Code Boundary** | `# DO NOT EDIT` immutable headers + CI AST checksums | Allowing freehand editing of generated graph code | Prevents drift between `impl_docs/` and the underlying runtime state machine. `impl_docs/` remains the single source of truth. |
| **B-4** | **Hook Dispatch Mechanism** | Explicit YAML path hook (`transform_handler: "handlers/mod.py::func"`) | Magic class inheritance or implicit file naming | Explicit string import paths are transparent, easily statically validated by `ast.parse`, and allow arbitrary naming conventions. |
| **B-5** | **Data Contract Implementation** | Pydantic v2 Models + Great Expectations Suites | Raw dictionaries, dataclasses, or JSONSchema | Pydantic provides runtime validation, serialization, and IDE autocomplete; Great Expectations provides batch-level SLA verification before stage processing. |
| **B-6** | **Runtime Portability** | Modular strategy templates (`langgraph`, `python_pipeline`, `streaming`) | Single universal runtime | Different DDLC agents have fundamentally different architectures (stateful graph vs. linear ETL vs. stream processor); strategy isolation allows adding new runtimes cleanly. |
| **B-7** | **Fix Loop Granularity** | Surgical re-prompting of Leaf Coder for handler test failures | Rebuilding the entire agent from scratch | Eliminates wasted computation and avoids accidental regressions in working stages during fix iterations. |
